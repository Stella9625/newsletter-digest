Production query plans without production data

The PostgreSQL query planner makes use of internal statistics to help it decide how to best execute a query. These statistics often differ between production data and development environments, which means the query plans used in production may not be replicable in development.

PostgreSQL 的查询计划器（query planner）利用内部统计信息（statistics）来帮助决定如何最佳地执行查询。这些统计信息在生产数据（production data）和开发环境（development environments）之间往往存在差异，这意味着生产环境中使用的查询计划可能无法在开发环境中复现。

PostgreSQL's new features now let you copy those statistics down to your development environment, allowing you to simulate the plans for production workloads without needing to copy in all of that data first.

PostgreSQL 的新特性现在允许你将这些统计信息复制到开发环境中，让你能够模拟生产工作负载的查询计划，而无需首先复制所有这些数据。

I found this illustrative example useful:

我发现这个说明性的示例很有用：

SELECT pg_restore_attribute_stats(
    'schemaname', 'public',
    'relname', 'test_orders',
    'attname', 'status',
    'inherited', false::boolean,
    'null_frac', 0.0::real,
    'avg_width', 9::integer,
    'n_distinct', 5::real,
    'most_common_vals', '{delivered,shipped,cancelled,pending,returned}'::text,
    'most_common_freqs', '{0.95,0.015,0.015,0.015,0.005}'::real[]
);

（代码示例：使用 pg_restore_attribute_stats 函数恢复属性统计信息）

This simulates statistics for a status column that is 95% delivered. Based on these statistics PostgreSQL can decide to use an index for status = 'shipped' but to instead perform a full table scan for status = 'delivered'.

这模拟了一个 status 列的统计信息，其中 95% 的值是 delivered。基于这些统计信息，PostgreSQL 可以决定对 status = 'shipped' 使用索引，而对 status = 'delivered' 则执行全表扫描（full table scan）。

I posted on the SQLite user forum asking if SQLite could offer a similar feature and D. Richard Hipp promptly replied that it has one already:

我在 SQLite 用户论坛上发帖询问 SQLite 是否能提供类似功能，D. Richard Hipp 迅速回复称它已经有了：

All of the data statistics used by the query planner in SQLite are available in the sqlite_stat1 table (or also in the sqlite_stat4 table if you happen to have compiled with SQLITE_ENABLE_STAT4). That table is writable. You can inject whatever alternative statistics you like.This approach to controlling the query planner is mentioned in the documentation:https://sqlite.org/optoverview.html#manual_control_of_query_plans_using_sqlite_stat_tables.See alsohttps://sqlite.org/lang_analyze.html#fixed_results_of_analyze.The ".fullschema" command in the CLI outputs both the schema and the content of the sqlite_statN tables, exactly for the reasons outlined above - so that we can reproduce query problems for testing without have to load multi-terabyte database files.

SQLite 查询计划器使用的所有数据统计信息都可以在 sqlite_stat1 表中找到（如果你使用 SQLITE_ENABLE_STAT4 编译，也可以在 sqlite_stat4 表中找到）。该表是可写的。你可以注入任何你想要的替代统计信息。这种控制查询计划器的方法在文档中有提及：https://sqlite.org/optoverview.html#manual_control_of_query_plans_using_sqlite_stat_tables。另请参阅 https://sqlite.org/lang_analyze.html#fixed_results_of_analyze。CLI 中的 .fullschema 命令会输出模式（schema）和 sqlite_statN 表的内容，正是出于上述原因——这样我们就可以在测试中重现查询问题，而无需加载多 TB 的数据库文件。

  • Avoid prompting. Jamey’s entire workflow is designed to minimize text prompting: “I try to avoid prompting at all costs in my process.” Instead of writing complex JSON prompts or detailed descriptions, she relies on style references, image references, and personalization codes to communicate visually with AI.

  • 避免使用提示词（Avoid prompting）。Jamey 的整个工作流程旨在最小化文本 prompting（提示）：“我在创作过程中尽量避免使用提示词。”她不编写复杂的 JSON 提示词或详细描述，而是依靠风格参考、图像参考和个性化代码来与 AI 进行视觉沟通。
