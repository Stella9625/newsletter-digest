Anti-patterns: things to avoid

Agentic Engineering Patterns>

智能体工程模式 >

There are some behaviors that are anti-patterns in our weird new world of agentic engineering.

在我们这个奇特的agentic engineering（智能体工程）新世界中，有些行为属于anti-patterns（反模式）。

Inflicting unreviewed code on collaborators

将未经审查的代码强加给协作者

This anti-pattern is common and deeply frustrating.

这种anti-pattern（反模式）很常见，且令人深感沮丧。

Don't file pull requests with code you haven't reviewed yourself.

不要提交包含你自己都未审查过的代码的pull requests（拉取请求，简称 PR）。

If you open a PR with hundreds (or thousands) of lines of code that an agent produced for you, and you haven't done the work to ensure that code is functional yourself, you are delegating the actual work to other people.

如果你打开一个包含数百（或数千）行由agent（智能体）为你生成的代码的 PR，而你自己没有做过确保这些代码功能正常的工作，那么你实际上是在将实际工作推卸给其他人。

They could have prompted an agent themselves. What value are you even providing?

他们自己本可以去prompt（提示）agent（智能体）。你到底提供了什么价值？

If you put code up for review you need to be confident that it's ready for other people to spend their time on it. The initial review pass is your responsibility, not something you should farm out to others.

如果你将代码提交审查，你需要确信它已经准备好让其他人投入时间。initial review pass（初步审查）是你的责任，而不是你应该外包给他人的事情。

A good agentic engineering pull request has the following characteristics:

一个好的agentic engineering（智能体工程）pull request（拉取请求）具有以下特征：

  • The code works, and you are confident that it works.Your job is to deliver code that works.
  • The change is small enough to be reviewed efficiently without inflicting too much additional cognitive load on the reviewer. Several small PRs beats one big one, and splitting code into separate commits is easy with a coding agent to do the Git finagling for you.
  • The PR includes additional context to help explain the change. What's the higher level goal that the change serves? Linking to relevant issues or specifications is useful here.
  • Agents write convincing looking pull request descriptions. You need to review these too! It's rude to expect someone else to read text that you haven't read and validated yourself.
  • 代码能够运行，并且你确信它能运行。你的工作是deliver code（交付代码）且代码能够运行。
  • 变更足够小，能够高效审查，而不会给审查者带来过多的额外cognitive load（认知负荷）。几个小的 PR 胜过一个大 PR，而且借助coding agent（编程智能体）帮你处理 Git 操作，将代码拆分成独立的 commits（提交）很容易。
  • PR 包含额外的上下文来帮助解释变更。该变更所服务的更高层级目标是什么？链接到相关的 issues（问题）或 specifications（规范）在此处很有用。
  • Agents（智能体）会写出看起来很有说服力的 pull request（拉取请求）描述。你也需要审查这些！期望别人阅读你自己都未阅读和验证过的文本是粗鲁的。
Given how easy it is to dump unreviewed code on other people, I recommend including some form of evidence that you've put that extra work in yourself. Notes on how you manually tested it, comments on specific implementation choices or even screenshots and video of the feature working go alongway to demonstrating that a reviewer's time will not be wasted digging into the details.

鉴于将unreviewed code（未经审查的代码）丢给其他人有多么容易，我建议包含某种形式的证据，证明你自己投入了额外的工作。关于你如何手动测试的注释、对特定实现选择的评论，甚至功能运行的截图和视频，都能大大证明审查者的时间不会被浪费在挖掘细节上。

Qwen 3.5 is exceptional

This story hits particularly hard right now because the Qwen 3.5 models appear to be exceptionally good.

这个消息此刻显得尤为沉重，因为 Qwen 3.5 系列模型似乎表现得异常出色。

I've not spent enough time with them yet but the scale of the new model family is impressive. They started with Qwen3.5-397B-A17B on February 17th - an 807GB model - and then followed with a flurry of smaller siblings in 122B, 35B, 27B, 9B, 4B, 2B, 0.8B sizes.

我还未能充分体验这些模型，但这个新模型家族的规模令人印象深刻。他们于 2 月 17 日首先发布了 Qwen3.5-397B-A17B——一个 807GB 的模型——随后陆续推出了一系列更小的兄弟模型，包括 122B、35B、27B、9B、4B、2B 和 0.8B 参数规模。

I'm hearing positive noises about the 27B and 35B models for coding tasks that still fit on a 32GB/64GB Mac, and I've tried the 9B, 4B and 2B models and found them to be notably effective considering their tiny sizes. That 2B model is just 4.57GB - or as small as 1.27GB quantized - and is a full reasoning and multi-modal (vision) model.

我听说 27B 和 35B 模型在编码任务上表现不俗，且仍能在 32GB/64GB 的 Mac 上运行，而我亲自尝试了 9B、4B 和 2B 模型，考虑到它们的微小体量，其效果确实显著。那个 2B 模型仅需 4.57GB——量化（quantized）后最小仅 1.27GB——却是一个完整的推理（reasoning）和多模态（multi-modal，视觉）模型。

It would be a real tragedy if the Qwen team were to disband now, given their proven track record in continuing to find new ways to get high quality results out of smaller and smaller models.

鉴于 Qwen 团队在持续探索新方法以从越来越小的模型中获得高质量成果方面已证明的出色记录，如果该团队现在解散，那将是一场真正的悲剧。

If those core Qwen team members either start something new or join another research lab I'm excited to see what they do next.

如果这些 Qwen 核心团队成员要么创办新的项目，要么加入其他研究实验室，我很期待看到他们接下来的举措。

Long-context + training efficiency: making “impossible” context windows practical

  • 87% attention-memory reduction for long-context training: A Together paper highlighted a hybrid of Context Parallelism plus Sequence Parallel-style head chunking, claiming training a 5M context window 8B model on 8×H100 (single node) and cutting attention memory footprint by up to 87% @rronak_. The tweet also calls out a practical gap: most RL (Reinforcement Learning) post-training for long-context frontier models is still done on only a fraction of the full context due to memory cost.

  • 长上下文训练的注意力内存减少 87%：Together 的一篇论文强调了上下文并行（Context Parallelism）与序列并行风格头部分块（Sequence Parallel-style head chunking）的混合方法，声称在 8×H100（单节点）上训练 500万上下文窗口的 80 亿参数模型，并将注意力内存占用减少高达 87% @rronak_。该推文还指出了一个实际差距：由于内存成本，大多数长上下文前沿模型的 RL（强化学习）后训练仍仅在完整上下文的一小部分上进行。

  • FlashOptim (Databricks): Open-source optimizer implementations (AdamW/SGD/Lion) that preserve update equivalence while cutting memory—tweet thread announces pip install flashoptim @davisblalock, and MosaicAI summarizes >50% training memory reduction, e.g., bringing AdamW training overhead from ~16 bytes/param down to 7 bytes (or 5 with gradient release) and reducing an example 8B finetune peak from 175 GiB → 113 GiB @DbrxMosaicAI.

  • FlashOptim（Databricks）：开源优化器实现（AdamW/SGD/Lion），在保持更新等效性的同时减少内存——推文宣布 pip install flashoptim @davisblalock，MosaicAI 总结称训练内存减少 50% 以上，例如将 AdamW 训练开销从约 16 字节/参数降至 7 字节（或释放梯度后 5 字节），并将一个 80 亿参数微调示例的峰值内存从 175 GiB 降至 113 GiB @DbrxMosaicAI。

  • Heterogeneous infra for RL: SkyPilot argues RL post-training should split workloads across beefy GPUs (trainer), cheap GPUs (rollouts), and high-memory CPUs (replay buffers); Job Groups provides a single YAML orchestration model with coordinated lifecycle and service discovery @skypilot_org.

  • RL 的异构基础设施：SkyPilot 认为 RL 后训练应将工作负载拆分到高性能 GPU（训练器）、廉价 GPU（rollouts/ rollout 生成）和大内存 CPU（回放缓冲区）；Job Groups 提供单一 YAML 编排模型，具备协调的生命周期和服务发现 @skypilot_org。

  • Kernel/toolchain gotchas: A CuTeDSL + torch.compile regression report notes ~2.5× slowdown for wrapped kernels (including RMSNorm “Quack” kernels) when made compile-compatible via custom ops—highlighting friction between kernel-level speed and graph compilation requirements @maharshii.

  • 内核/工具链陷阱：一份 CuTeDSL + torch.compile 的回归报告指出，当通过自定义算子使包装内核（包括 RMSNorm "Quack" 内核）兼容编译时，会出现 约 2.5 倍减速——凸显了内核级速度与图编译需求之间的摩擦 @maharshii。
