Quoting Georgi Gerganov
本地模型编程代理工具链
Georgi Gerganov指出，本地模型难以与coding agents良好配合的主要症结在于，从输入到输出的漫长链条涉及多个由不同方开发的脆弱组件（包括框架、聊天模板和提示词构建等）。由于整个技术栈难以整合，用户当前得到的结果很可能在某些环节仍存在细微缺陷。
From typing the task in the client to the actual result, there is a long chain of components that atm are not only fragile - are also developed by different parties.
从在客户端输入任务到获得实际结果，其中涉及一长串组件链条，这些组件不仅脆弱，而且由不同团队开发。
What you are currently observing is with very high probability still broken in some subtle way along that chain.
你当前观察到的结果，极有可能在这个链条的某个细微环节上仍然存在问题。

Quoting Georgi Gerganov

Note that the main issues that people currently unknowingly face with local models mostly revolve around the harness and some intricacies around model chat templates and prompt construction. Sometimes there are even pure inference bugs. From typing the task in the client to the actual result, there is a long chain of components that atm are not only fragile - are also developed by different parties. So it's difficult to consolidate the entire stack and you have to keep in mind that what you are currently observing is with very high probability still broken in some subtle way along that chain.

请注意，人们当前在运行本地模型（local models）时无意中遇到的主要问题，大多围绕着工具链（harness）以及模型对话模板（model chat templates）和提示词构建（prompt construction）的一些细微复杂性。有时甚至存在纯粹的推理错误（inference bugs）。从在客户端输入任务到获得实际结果，其间存在一长串组件链条，这些组件目前（atm）不仅十分脆弱——而且由不同的团队开发。因此很难整合整个技术栈，你必须牢记：你目前观察到的结果，极大概率仍然在该链条的某个微妙环节存在问题。

Note that the main issues that people currently unknowingly face with local models mostly revolve around the harness and some intricacies around model chat templates and prompt construction. Sometimes there are even pure inference bugs. From typing the task in the client to the actual result, there is a long chain of components that atm are not only fragile - are also developed by different parties. So it's difficult to consolidate the entire stack and you have to keep in mind that what you are currently observing is with very high probability still broken in some subtle way along that chain.

请注意，人们当前在运行本地模型（local models）时无意中遇到的主要问题，大多围绕着工具链（harness）以及模型对话模板（model chat templates）和提示词构建（prompt construction）的一些细微复杂性。有时甚至存在纯粹的推理错误（inference bugs）。从在客户端输入任务到获得实际结果，其间存在一长串组件链条，这些组件目前（atm）不仅十分脆弱——而且由不同的团队开发。因此很难整合整个技术栈，你必须牢记：你目前观察到的结果，极大概率仍然在该链条的某个微妙环节存在问题。

Steve Kaliski has spent over six years building developer infrastructure at Stripe. In this conversation with Claire, he breaks down Stripe's "minions": AI coding agents that ship about 1,300 pull requests per week, often kicked off with nothing more than a Slack emoji. He explains why the real bottleneck in engineering isn't coding, how cloud development environments unlock parallel AI workflows, and what it takes to safely review thousands of AI-generated PRs. He also demos AI agents that can spend money, coordinate services, and complete tasks end-to-end without human involvement.

Steve Kaliski 已在 Stripe 工作六年多，负责构建开发者基础设施。在本期对话中，他向 Claire 详细解析了 Stripe 的“小黄人”（minions）：每周能提交约 1,300 个拉取请求（pull request）的 AI 编程智能体（AI coding agents），通常只需一个 Slack 表情即可触发。他解释了工程领域的真正瓶颈并非编写代码，云开发环境（cloud development environments）如何解锁并行的 AI 工作流，以及如何安全地审查数千个 AI 生成的 PR。他还演示了能够自主花钱、协调服务并在无需人工干预的情况下端到端完成任务的 AI 智能体。

Biggest takeaways:

核心要点：

  • What's good for human developers is good for AI agents (and vice versa). Stripe's years of investment in developer experience—comprehensive documentation, blessed paths for common tasks, robust CI/CD, excellent tooling—directly translates to higher AI agent success rates. When you have clear docs on "how to add a new API field," the agent can follow those same instructions. This creates a virtuous cycle: investments in DX improve agent performance, and investments in agent infrastructure (like cloud environments) benefit human developers too.

  • 对人类开发者有益的东西对 AI 智能体（AI agents）同样有益（反之亦然）。Stripe 多年来对开发者体验（DX）的投入——全面的文档、通用任务的标准路径（blessed paths）、强大的 CI/CD（持续集成/持续部署）流程、优秀的工具链——直接转化为更高的 AI 智能体成功率。当你有清晰的文档说明“如何添加新的 API 字段”时，智能体也能遵循同样的指令。这形成了一个良性循环：对 DX 的投资提升了智能体性能，而对智能体基础设施（如云环境）的投资也惠及人类开发者。

  • Activation energy is the real bottleneck, not coding speed. Steve hasn't started work in a text editor in months. Instead, work begins in Slack threads, Google Docs, or support tickets—the natural places where ideas emerge. By allowing engineers to kick off development with a single emoji reaction, Stripe lowered the friction between "good idea" and "code in production."   • 启动能量（activation energy）才是真正的瓶颈，而非编码速度。Steve 已经数月没有在文本编辑器中开始工作了。相反，工作始于 Slack 线程、Google Docs 或支持工单——这些想法自然涌现的地方。通过允许工程师用单个表情符号触发生成代码，Stripe 降低了从“好想法”到“生产环境代码”之间的摩擦。这在大型组织中尤为强大，因为协调成本通常会在编码开始之前就扼杀动力。

  • 云开发环境（cloud development environments）对于多线程 AI 工作是不可或缺的。并行运行多个 AI 智能体需要能在几秒钟内启动、运行隔离工作负载且永不休眠的云开发环境。这项基础设施投资——由 Stripe 的开发者生产力团队在 AI 智能体出现之前很久就构建好了——现在使工程师能够同时运行数十个智能体，而不会让他们的 MacBook Pro 过热。

  • 1,300 AI-written PRs per week requires shifting review capacity, not eliminating it.   • 每周 1,300 个 AI 编写的 PR 需要转移审查能力，而非消除审查。Stripe 仍然审查每一个 AI 生成的 PR，但审查过程严重依赖自动化的置信度信号：全面的测试覆盖、合成端到端测试，以及支持快速回滚的蓝绿部署（blue-green deployments）。瓶颈从编写代码转移到了审查代码——最终转移到了最初产生足够多的好想法。

  • Treat AI agents like new employees, with progressive trust. Start with limited access, expand permissions as the agent proves reliable, and maintain clear boundaries.   • 像对待新员工一样对待 AI 智能体，采用渐进式信任（progressive trust）。从有限的访问权限开始，随着智能体证明其可靠性而逐步扩展权限，并保持清晰的边界。每个小黄人在隔离的环境中运行，具有特定的数据访问权限——财务智能体可以读取银行对账单但不能发送消息；日程安排智能体可以发短信但没有财务数据访问权限。这种物理分区防止了意外的数据泄露并建立了问责制。

Trip Venturella released Mr. Chatterbox, a language model trained entirely on out-of-copyright text from the British Library. Here's how he describes it:

Trip Venturella 发布了 Mr. Chatterbox，这是一个完全基于大英图书馆（British Library）公有领域文本训练的语言模型（language model）。以下是他的描述：

Mr. Chatterbox is a language model trained entirely from scratch on a corpus of over 28,000 Victorian-era British texts published between 1837 and 1899, drawn from a dataset made available by the British Library. The model has absolutely no training inputs from after 1899 — the vocabulary and ideas are formed exclusively from nineteenth-century literature. Mr. Chatterbox's training corpus was 28,035 books, with an estimated 2.93 billion input tokens after filtering. The model has roughly 340 million paramaters, roughly the same size as GPT-2-Medium. The difference is, of course, that unlike GPT-2, Mr. Chatterbox is trained entirely on historical data.

Mr. Chatterbox 是一个完全从零开始训练的语言模型，训练语料库（corpus）包含超过 28,000 本出版于 1837 至 1899 年间的维多利亚时代英国文本，数据来自大英图书馆开放的数据集。该模型完全没有使用 1899 年之后的任何训练输入——其词汇和概念完全形成于十九世纪文学。Mr. Chatterbox 的训练语料共 28,035 本书，经过滤后估计包含 29.3 亿个输入词元（input tokens）。模型拥有约 3.4 亿个参数（parameters），规模大致与 GPT-2-Medium 相当。当然，区别在于与 GPT-2 不同，Mr. Chatterbox 完全基于历史数据训练。

鉴于在不使用大量抓取的无授权数据的情况下训练一个有用的大语言模型（LLM, Large Language Model）是如此困难，我多年来一直梦想着这样的模型。一个完全基于公有领域（out-of-copyright）文本训练的模型会是什么样的聊天体验？

Honestly, it's pretty terrible. Talking with it feels more like chatting with a Markov chain than an LLM - the responses may have a delightfully Victorian flavor to them but it's hard to get a response that usefully answers a question.

老实说，它相当糟糕。与其对话的感觉更像是与马尔可夫链（Markov chain）聊天，而非大语言模型——虽然回复可能带有令人愉悦的维多利亚时代风味，但很难得到真正有用地回答问题的回应。

The 2022 Chinchilla paper suggests a ratio of 20x the parameter count to training tokens. For a 340m model that would suggest around 7 billion tokens, more than twice the British Library corpus used here. The smallest Qwen 3.5 model is 600m parameters and that model family starts to get interesting at 2b - so my hunch is we would need 4x or more the training data to get something that starts to feel like a useful conversational partner.

2022 年 Chinchilla 论文建议参数数量与训练词元的比例为 1:20。对于 3.4 亿参数的模型，这意味着需要约 70 亿词元，是此处使用的大英图书馆语料库的两倍多。最小的 Qwen 3.5 模型有 6 亿参数，而这个模型家族在 20 亿参数时才开始变得有趣——因此我的直觉是，我们需要四倍或更多的训练数据才能获得一个感觉上有用的对话伙伴。

But what a fun project!

但这是一个多么有趣的项目啊！

Running it locally with LLM

I decided to see if I could run the model on my own machine using my LLM framework.

我决定看看是否能使用我的 LLM 框架在自己的机器上运行这个模型。

I got Claude Code to do most of the work - here's the transcript.

我让 Claude Code 完成了大部分工作——这是对话记录。

Trip trained the model using Andrej Karpathy's nanochat, so I cloned that project, pulled the model weights and told Claude to build a Python script to run the model. Once we had that working (which ended up needing some extra details from the Space demo source code) I had Claude read the LLM plugin tutorial and build the rest of the plugin.

Trip 使用 Andrej Karpathy 的 nanochat 训练了该模型，因此我克隆了该项目，拉取了模型权重，并让 Claude 编写了一个 Python 脚本来运行模型。一旦运行成功（最终需要从 Space 演示源代码 获取一些额外细节），我让 Claude 阅读 LLM 插件教程并构建了插件的其余部分。

llm-mrchatterbox is the result. Install the plugin like this:

llm-mrchatterbox 就是最终的成果。安装该插件的方法如下：

llm install llm-mrchatterbox
The first time you run a prompt it will fetch the 2.05GB model file from Hugging Face. Try that like this:

第一次运行提示时，它会从 Hugging Face 获取 2.05GB 的模型文件。像这样尝试：

llm -m mrchatterbox "Good day, sir"
Or start an ongoing chat session like this:

或者像这样启动一个持续的聊天会话：

llm chat -m mrchatterbox
If you don't have LLM installed you can still get a chat session started from scratch using uvx like this:

如果你还没有安装 LLM，你仍然可以使用 uvx 从零开始启动一个聊天会话：

uvx --with llm-mrchatterbox llm chat -m mrchatterbox
When you are finished with the model you can delete the cached file using:

使用完模型后，你可以使用以下命令删除缓存文件：

llm mrchatterbox delete-model
This is the first time I've had Claude Code build a full LLM model plugin from scratch and it worked really well. I expect I'll be using this method again in the future.

这是我第一次让 Claude Code 从零开始构建一个完整的 LLM 模型插件，效果非常好。我预计将来会再次使用这种方法。

I continue to hope we can get a useful model from entirely public domain data. The fact that Trip was able to get this far using nanochat and 2.93 billion training tokens is a promising start.

我仍然希望我们能够从完全公有领域（public domain）的数据中获得一个有用的模型。Trip 能够使用 nanochat 和 29.3 亿训练词元走到这一步，是一个充满希望的开始。

Function Calling Harness: From 6.75% to 100% (32 minute read)

AutoBe is an open-source AI Agent that takes a single natural language conversation and generates a complete backend. qwen3-coder-next has a 6.75% function calling success rate when asked to generate API data types for a shopping mall backend. AutoBe boosts that success rate up to over 99.8%. It uses a Harness where type schemas constrain outputs, compilers verify results, and structure feedback pinpoints compactly where and why something went wrong so the agent can correct itself. This post dissects the engineering behind AutoBe.

AutoBe 是一个开源的 AI Agent（AI 智能体），它接受单一的自然语言对话并生成完整的后端。qwen3-coder-next 在被要求为商场后端生成 API 数据类型时，Function Calling（函数调用）成功率仅为 6.75%。AutoBe 将该成功率提升至超过 99.8%。它使用一种 Harness（约束框架），其中类型模式（Type Schemas）约束输出，编译器验证结果，结构化反馈精确定位出错的位置和原因，以便智能体能够自我纠正。本文剖析了 AutoBe 背后的工程原理。

前沿 AI 的能力提升并未导致相对于人工劳动的 Inference Costs（推理成本）增加。尽管每项任务的推理成本在上升，但当前模型完成任务的成本大约仅为人工成本的 3%，且成本比率中位数没有上升趋势。模型即使在严格的成本约束下也能继续进步，使得 AI 成本比率保持在远低于人工水平的情况下实现可盈利的自动化。

This article analyzes the loop to see what makes it so successful.

Pretext 是一种快速、准确、全面的文本测量算法，它可以在不依赖 DOM（Document Object Model，文档对象模型）测量和重排（Reflow）的情况下布局网页。它是使用 AI 智能体工作流创建的。开发该工具时使用的特定循环（约束 -> 测量 -> 隔离 -> 分类 -> 测试 -> 拒绝 -> 只保留经受住广泛压力的部分）使工程变得严谨。本文分析了该循环，以探究其成功的原因。
